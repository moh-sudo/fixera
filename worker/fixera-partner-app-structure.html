00 Overview

The Fixera Partner App is a unified React web application that serves four distinct partner roles — Workers, Vendors, Riders, and Suppliers — under one codebase. Role-based permissions control what each partner sees and can do.

02 The Four Partner Roles

🔧
Service Worker
/dashboard
Accepts home service jobs — plumbing, electrical, painting, cleaning. Tracks live jobs, earns per completed booking.
🏪
Vendor
/vendor/dashboard
Manages laundry and carpet wash orders. Has open/closed toggle. Accepts incoming orders and marks them complete.
🚗
Rider
/rider/dashboard
Accepts pickup/delivery jobs. Goes online to see available runs. Updates delivery status step-by-step. Earns KSh 300 per delivery.
📦
Supplier
/supplier/dashboard
Lists products (paint, tools, cleaning supplies). Products are recommended to customers who book related services.

05 Route Protection (ProtectedRoute.jsx)

Every dashboard route passes through three layers of protection:

LAYER 1
Auth Guard
if (loading) → show spinner  |  if (!user) → redirect to /login
Prevents unauthenticated access to any dashboard.
LAYER 2
Onboarding Gate
if (onboarding_complete === false) → redirect to /onboarding
Applies to ALL roles — no partner skips the verification wizard.
LAYER 3
Role Guard
if (allowedRoles && role not in allowedRoles) → redirect to own dashboard
Prevents a rider from accessing /vendor/dashboard etc.

10 Key Design Decisions

1
One app, four roles
Instead of building 4 separate apps, one codebase serves all partners. Role is stored as partner_role in the workers table and controls routing, navigation, and dashboard content. Easier to maintain, deploy, and update.
2
Onboarding before dashboard
Every new partner must complete the verification wizard before accessing any dashboard. This ensures Fixera collects all compliance documents upfront — ID, certifications, criminal declarations, business registration.
3
RLS at database level
Security lives in Supabase Row Level Security, not the React app. Even if someone bypasses the frontend, they can never read or modify another partner's data. auth.uid() = id is enforced at the database engine.
4
service_details JSONB
Instead of creating separate tables for each role's onboarding data, all answers are stored in a single JSONB column. This keeps the schema simple while supporting unlimited flexibility — each role stores completely different fields.
5
Verification flow
After onboarding, verification_status = 'pending'. Admin reviews all documents in the Admin Dashboard and sets it to 'approved'. Partners can access dashboards immediately but won't receive jobs until approved by admin.
